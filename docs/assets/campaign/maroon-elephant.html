You added the AI feature in an afternoon, and that was rather the problem. A model client, a prompt, a tool the model is allowed to call on your behalf, and a cheerful stretch of user text poured straight into the top of it. It worked on the first try, which is always the moment to be nervous. You shipped it. And some quiet evening a few weeks later, long after the demo applause has faded, a small cold thought arrives: you have no earthly idea what you just exposed.

You reach for the security tools you already trust, and they have nothing useful to say. They hunt for SQL injection and hardcoded passwords, and they are very good at it, and they will walk straight past a model you have handed a shell and a secret and a stranger's instructions, all in the same breath, without so much as a raised eyebrow. The scanner is not wrong. It is simply looking for last decade's mistakes.

Here is the thing worth understanding, because it is the root of nearly everything that goes wrong. A language model collapses the control plane and the data plane into one flat token namespace. In a sane system, instructions live in one channel and data in another, and the machine knows which is which. A model knows no such distinction. The command and the content arrive as the same undifferentiated stream of tokens, and the model obeys whichever sounds most persuasive. That single architectural fact is the parent of prompt injection, of quiet data exfiltration, of an agent granted far too much agency, of a memory slowly poisoned. The security market has answered this with a crowd of runtime products that watch the model in production. Open-source, repo-driven, design-time threat modeling, the sort you can run before a single token is spent, has been thin on the ground.

So I built one. It is called Maroon Elephant. It reads a repository, works out which parts of it are AI, agentic, or MCP machinery, infers the architecture, and produces evidence-backed threat findings mapped to the OWASP 2026 families: the LLM Top 10, the Agentic Top 10, GenAI Data Security, and the MCP guidance. Worst first, and across a whole organisation if you point it at one.

It works deterministically before it works cleverly, and the order matters enormously. Every finding it reports carries `file:line` evidence, because a rule found an actual pattern in your actual code. The optional language model, if you switch it on, may only enrich a finding that already exists. It describes; it never invents. A scanner that can hallucinate a vulnerability is a scanner that will one day cost you a weekend chasing a ghost, and this one is built so it cannot.

Running it is the dull part, which is exactly as it should be.

pip install maroon-elephant
maroon scan .
maroon scan ./app --format sarif -o results.sarif

Allow me a paragraph of respect for the genuinely hard part, because it is hard and it is where the real work went. A finding is only useful if you can recognise it again tomorrow. So each one gets a fingerprint computed from the lexical shape of the code around it, which means you can reindent the file, or shove the whole block two hundred lines down, and the tool still knows it is the same finding. Change the code itself, and the fingerprint changes, as it should. This is fiddlier than it sounds. An early version let two identical blocks at different lines collapse into one, which quietly hid new vulnerabilities behind a `--baseline` diff. That bug was found, reproduced, and killed with an occurrence disambiguator and a test written specifically to attack it. The taint analysis is the same story: it follows a model's output through assignments inside a function, by fixpoint, until it reaches a dangerous sink such as `eval`, `os.system`, or a database cursor. Getting that reassembly right, and honest about its edges, was the whole game.

Now the disappointment, delivered on purpose, because it is the most trustworthy thing I can offer you. Maroon Elephant does static analysis only. It will not run your code, so it produces no runtime findings. Its taint tracking is intraprocedural: it reasons inside one function and does not chase a tainted value across a function boundary, and it only recognises sinks that are named plainly, so a cunning `getattr(os, "system")(x)` will slip past it. Expect false negatives there, and plan for them. The Lethal-Trifecta check, which looks for untrusted input, sensitive data, and an exit route huddled together near a model call, is a file-level heuristic. It is a prompt to go and look, and it can over-flag or under-flag. The governance checks cannot see controls that leave no trace in source, so those are reported as "needs attestation" and never as a pass. The dependency check is fingerprint-based against a curated set of known exploits, so pair it with a full scanner such as OSV-Scanner for breadth. And the whole thing is honestly labelled alpha, under active construction. Deep taint runs natively for Python and, through the optional `[polyglot]` extra, for JavaScript, TypeScript, Go, and Java.

On the matter of its own security I was deliberately severe, because a tool that scans for weakness has no business harbouring any. The core has zero runtime dependencies. It is the Python standard library and nothing else, which is a promise about your supply chain as much as your disk. It is local-first and bring-your-own-key: your source never leaves your machine by default, and in air-gapped mode it makes zero external calls. Keys are never written to a log. When it clones a repository by URL it allows only sane schemes and blocks cloud-metadata and link-local hosts, so a hostile URL cannot turn the cloner into a weapon aimed at your own network. The local dashboard carries a per-process CSRF token, a Host allowlist, and a guard against DNS rebinding. Zip ingestion refuses path traversal and symlinks and caps decompression against zip bombs. Every run is written to a hash-chained, tamper-evident log. And it scans itself in CI, where the self-scan must come back clean before a release ships. The hardening was done adversarially, three rounds of a fresh reviewer trying to break it, and the final count stands at 57 tests passing.

What is it all for, underneath? Sight, mostly. The quiet point of the thing is to make the attack surface of an AI system visible at the moment you can still cheaply do something about it, which is before you ship. It gives you three things you can hold: a list of findings you can feed straight into GitHub code scanning as SARIF, a design-time threat model of how your components actually talk to one another, and an AI inventory, a bill of materials that finally answers the sheepish question every team eventually asks itself, which is what AI are we even running. And because every finding carries a cross-framework tuple, mapping it to OWASP, to MITRE ATLAS, to CWE, to the relevant regulation, a report stops being one engineer's nervous opinion and becomes something a committee will respect.

The defining virtue is the evidence. Everything it tells you, it can show you, down to the line that earned the accusation, and the one part that might have made things up is the one part forbidden from inventing anything at all.

It is Apache-2.0, and it is honest about what it cannot see. That turns out to be the most useful thing about it.
