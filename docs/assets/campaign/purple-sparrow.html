You have handed a coding agent a job against a backend, and you have watched what it does next. It fires a request, confident as a surgeon, and the backend answers with a bare 403, or an empty list where rows plainly ought to sit, and not one word about why. The agent reads that silence the only way it can. It guesses. It tries a different endpoint, invents a header, strips a filter it should have kept, and carries on with the serene certainty of someone who has misread the room and has no idea. A minute later your data is in a shape you never asked for, and the only clue left behind is a query that returned nothing at all.

The maddening part is that the agent was never told anything. Not what it did wrong. Not how to set it right. Not even where the door was.

Hold that frustration up to the light and turn it over, because the fault is older than any agent. The backends most of us reach for were built for a human with a mouse. They assume a person will sit at a dashboard, click through a settings page, read the small print, and notice when a toggle is off. A coding agent does none of that. It arrives through the API and only the API, and against that visitor a generic backend fails three ways. It fails silently, handing back an error with no account of itself. It leaks, because the access rule that should have been there was never written and nothing complained. And it hides, because the shape of the thing lives in a dashboard the agent cannot see. Three failures, one root. The backend was written for the wrong reader.

So I built one for the right reader. It is called Purple Sparrow, and it is a backend-as-a-service for AI coding agents, shipped as a single static Go binary with SQLite embedded inside it. No external services to stand up, no sidecar, nothing to install beside it. You run the binary and you have a backend.

The whole design follows from a single assumption, which is that the thing operating this backend is a machine, and a machine can recover from almost anything if you tell it the truth. So the backend tells it the truth, at every turn.

It tells the truth about access first. Every table is deny-by-default. A freshly created table returns nothing to anyone until you write a policy that opens it, because the most expensive bug in this corner of software is the access rule nobody remembered to add. Watch how plainly it falls out in practice.

PS_ADMIN_API_KEY=ps_sk_dev ./purplesparrow            # → 127.0.0.1:8787
ADMIN="Authorization: Bearer ps_sk_dev"

# create a table (id + created_at are automatic)
curl -s -H "$ADMIN" -X POST localhost:8787/v1/tables \
  -d '{"name":"todos","columns":[{"name":"title","type":"text"}]}'

# the table exists, yet reads return nothing: access is denied until granted
curl -s -H "$ADMIN" -X POST localhost:8787/v1/policies \
  -d '{"table":"todos","action":"select","roles":["anon"],"using":"true"}'

That policy is where the genuinely hard engineering lives, and it deserves a paragraph of respect. When you write a rule like `owner_id = auth.uid()`, Purple Sparrow does not paste that string anywhere near your database. It runs it through a small compiler of its own, a lexer and a parser and a code generator, which walks the expression and emits parameterised SQL. Column names are checked against an allow-list before a single one is quoted as an identifier. Every other value, every literal and every `auth.uid()`, is bound as a placeholder and never written into the query text. The compiler fails closed. Hand it an operator it does not know or a column it has never heard of, and it refuses to produce SQL rather than produce SQL you did not mean. It is fuzz-tested precisely because this is the one place where a mistake is unforgivable. A rule that governs who may read your data must never, under any input, emit a raw literal into a statement.

Then it does the quieter, harder half. The same rule is enforced twice: once as a `USING` filter, so a read only sees the rows it is allowed to see, and once as a `WITH CHECK` condition, so a write only lands a row the author is allowed to land. Writes that read and then modify run inside one transaction with the row locked, so the check cannot be raced out from under you. And every bit of this behaves identically whether SQLite is underneath for a solo laptop or Postgres is underneath for scale, with a conformance suite that runs the security behaviours against a real Postgres in CI to prove the two engines agree. One rule, one meaning, two databases, no drift.

The truth-telling does not stop at access. When the agent does hit a wall, the error that comes back is a contract, not a shrug. Every non-2xx response across the whole service carries a stable code, a plain message, a `remediation` hint, and a list of concrete `next_actions`. When the agent is stuck, the response itself tells it how to get unstuck, which is the single affordance that lets an agent repair its own work instead of flailing. And the shape of the backend is reachable in one call: `GET /meta` returns the whole thing at once, the docs are served over the API rather than hidden in a dashboard, and an advisor endpoint lints your configuration and points at the risky parts before they bite. Point Cursor or Claude at it with the built-in MCP server and the entire surface becomes a set of tools the agent can hold directly.

Now let me disappoint you a little, on purpose, because the honesty is the point and not the footnote.

Purple Sparrow is in beta. The full surface is built and tested end to end, data and policy, auth with RS256 tokens and rotating refresh, storage, sandboxed WASM functions, realtime over SSE, an embedded dashboard, but built and tested is not the same as proven under fire, and I will not pretend it is. The policy engine, the one piece everything else trusts, warrants an independent security audit before you put regulated data behind it. Realtime fan-out is per-node today; a shared bus for spreading events across nodes is the next job, not a finished one. The memory cap on functions is process-wide rather than per-function. Postgres and S3 are verified in CI and have not yet carried a real production load. These are the map, drawn honestly, so you can decide what to trust it with. A limit you can read is worth far more than a reassurance you cannot.

Where it is firm, it is firm on purpose. Access is deny-by-default everywhere. Secrets and API keys are stored hashed and never written to a log; the error envelope logs internal detail on the server and never serialises it to the client, so nothing leaks through the crack. The database file is locked to `0600`, the data directory to `0700`, and the non-solo tiers flatly refuse to boot without an explicit admin key. There is per-IP rate limiting, a content-security policy and the usual security headers, and the container image is non-root and distroless. The quality gates run on every change: the race detector, `go vet`, `staticcheck`, and `govulncheck`, all green, with that Postgres parity proven alongside. It is Apache-2.0, built in the open, and affiliated with no other backend platform.

What is it really for, underneath all of that? Trust of a specific and unglamorous kind. The freedom to hand an agent a real job against a real backend and not hover over its shoulder, because the backend will refuse what should be refused, explain every refusal in words the agent can act on, and describe its own shape on request. You stop being the interpreter between a confident machine and a silent one. The agent asks, the backend answers truthfully, and the work moves.

That is the whole personality of the thing. It keeps the door locked until you open it, and when it turns you away it tells you exactly how to be let in.
